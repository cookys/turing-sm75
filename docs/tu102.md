## 整顆晶片 hierarchy

```
TU102 die（TSMC 12 nm FFN，754 mm²，186 億電晶體）
 └─ 6 × GPC
      └─ 每 GPC：1 raster engine + 6 × TPC
           └─ 每 TPC：2 × SM + 4 texture units（每 SM 4 個 TEX，TPC 共 8？官方：每 SM 4 TEX；滿血 288 TEX = 72×4）
                └─ 每 SM：4 × processing block（SMSP）+ 共用 96 KB L1/smem + 1 RT Core

記憶體側（跟 SM 分開）：
  滿血 12 × 32-bit GDDR6 控制器 = 384-bit
  每個控制器：8 ROP + 512 KB L2
  → 滿血 96 ROP、6144 KB L2
```

滿血 TU102：6×6×2 = **72 SM**。

這張 2080 Ti 是砍過的（官方表 vs 本機 prop）：

| | 滿血 TU102 / Quadro RTX 6000 | **這張 RTX 2080 Ti** |
|---|---:|---:|
| GPC | 6 | 6 |
| TPC | 36 | **34** |
| SM | 72 | **68**（本機） |
| CUDA core（64／SM） | 4608 | 4352 |
| Tensor Core（8／SM） | 576 | **544** |
| RT Core | 72 | 68 |
| TEX | 288 | 272 |
| GDDR6 控制器 | 12 × 32-bit = 384-bit | **11 × 32-bit = 352-bit** |
| L2 | 12 × 512 = 6144 KB | **11 × 512 = 5632 KB**（本機） |
| ROP | 96 | 88 |
| 帳面頻寬 @ 14 Gbps | 672 GB/s | **616 GB/s** |
| 這台 VRAM | — | **22528 MiB**。同 352-bit，顆粒比較密；**頻寬不會變** |

L2 跟控制器綁在一起。少一個控制器 = 少 512 KB L2，不是「cache 隨便縮水」。

NVLink：TU102 有兩條 x8（雙向合計 100 GB/s）。這張單卡用不到。

## SM 內部 layout

每個 SM **不是**一個大池。切成 **4 個 processing block（SMSP）**。

```
                    ┌──────────── 一個 SM ────────────┐
                    │  共用：96 KB L1/smem/TEX cache   │
                    │  共用：1 × RT Core、2 × FP64     │
     ┌──────────┬──────────┬──────────┬──────────┐
     │ SMSP 0   │ SMSP 1   │ SMSP 2   │ SMSP 3   │
     │ sched×1  │ sched×1  │ sched×1  │ sched×1  │
     │ dispatch │          │          │          │
     │ L0 I$    │          │          │          │
     │ RF 64 KB │ RF 64 KB │ RF 64 KB │ RF 64 KB │
     │ 16 FP32  │ 16 FP32  │ 16 FP32  │ 16 FP32  │
     │ 16 INT32 │ 16 INT32 │ 16 INT32 │ 16 INT32 │
     │ 2 TC     │ 2 TC     │ 2 TC     │ 2 TC     │
     └──────────┴──────────┴──────────┴──────────┘
        warp 靜態分配給四個 scheduler，不能漂去別的 SMSP
```

每個 SM 合計：64 FP32、64 INT32、8 TC、256 KB 暫存器、4 scheduler。

### Warp 怎麼對到 scheduler

Warp **靜態**分給四個 scheduler。一個 4-warp 的 block（我們 occ* 的 `block=(32,4)`）= 每個 SMSP 剛好一條 warp，四個 scheduler 都有事做。

一個 8-warp 的 block（wmma `256` thread）= 每個 SMSP 兩條 warp。

### 暫存器：按 SMSP 算，不要只看 65536

本機：`regsPerMultiprocessor = 65536`、每 thread 上限 255。  
切開：`65536 / 4 = 16384` 個 32-bit／SMSP。

```
32 × regs_per_thread × warps_on_that_SMSP  ≤  16384
```

整顆 SM 的 warp 上限還有一條：**32 warp／SM**（Turing；Volta 是 64）。  
threads／SM 上限 1024；blocks／SM 上限 16。

| 設計 | 算式 | 每個 SMSP 能住 | 整顆 SM |
|---|---|---:|---|
| 255 regs、1 warp | 32×255=8160 | 1 | 4 warp＝12.5% |
| **255 regs、2 warp** | 32×255×2=**16320** | **2（卡死）** | 8 warp＝25% ← serial / wmma |
| 38 regs、8 warp（occ） | 32×38×8=9728 | 8 | 32 warp＝100% |
| 47 regs、8 warp（occ2） | 12032 | 8 | 32 |
| **62 regs、8 warp（occ4）** | **15872** | **8（距 16384 還有 512）** | **32＝100%** |
| 64 regs、8 warp | 16384 剛好 | 8 | 32 |
| 70 regs、8 warp | 17920 **超** | 掉成 6 | 24 warp＝75% |

`regs > 64` 且還想維持 8 warp／SMSP 就會掉 occupancy。寫新 kernel 先把這個不等式算完。

Spill：超過 255 或 ptxas 塞不下會進 local memory。Turing L1 可 cache spill，代價仍比暫存器高。serial 255 + 84 B spill 就是這條。

## 數學管線與延遲

Tuning Guide 原文要義：

- 每個 scheduler 一拍發 **一條**獨立指令；指令本身跨 **2 cycle** 做完
- 核心 FMA 的相依延遲是 **4 cycle**（Pascal 是 6）
- **每 warp 4-way ILP → 4 warp／SM 就能藏延遲**
- **沒有 ILP → 要 16 warp／SM**

INT32 與 FP32 **各有 64 顆、可同時發**。官方量過現代 shader 大約每 100 條 FP 混 36 條 INT（位址、min/max、比較）。把 INT 搬走，FP 理論再多約 36% 吞吐。

刻序列迴圈時：

- 這一 token 的 FMA 進行時，用 INT 管線算下一 token 的指標、發 `LDG`
- 不要把位址算術跟 FMA 寫成完全相依的一條鏈

獨立執行緒排程（Volta+ 繼承）：**沒有隱含 warp 同步**。warp reduce 要用 `__shfl_*_sync` / `__syncwarp`。ggml 的 `warp_reduce_sum` 已經這樣做。

### FP16 CUDA 運算走哪條管線

Turing 起，純 FP16 的 `HADD2`／`HMUL2` 改走 **Tensor Core／MMA 管線**，不是 64 顆 FP32 CUDA core。後果：

- `HADD2` 可以跟 `FFMA` 或 `IADD` 雙發（第三條選擇）
- **`HADD2` 跟 `HMMA` 互搶**。softmax／rescale 用 fp16 CUDA core「免費重疊在 TC 旁邊」在這顆上不成立
- SASS 看到大量 `HADD2` 的「TC kernel」可能 MMA pipe 被自己的 epilogue 堵住

## Tensor Core（第二代）

官方：每顆 TC 每拍最多 **64 次 FP16 FMA**（硬體 4×4×4）。8 顆 → 每 SM 每拍 512 FMA = **1024 FLOP**。

INT8 模式是這個速率的兩倍；INT4 再兩倍。這就是帳面 215／430 TOPS 的來源。

硬體指令：**`HMMA.1688`**（16×8×8，fp16 進、f32 或 f16 累加）。我們 attn SASS 看到的就是這個。

### 軟體怎麼對到硬體

| 你寫的 | 這顆 sm_75 實際變成 | 何時用 |
|---|---|---|
| `nvcuda::wmma` 16×16×16 | 編譯成 **兩發** `HMMA.1688` | 能動；layout／bank 較差 |
| `mma.sync.aligned.m16n8k8.row.col.f32.f16.f16.f32` | **一發對一發** | 該走的路。CUTLASS、`mma.cuh` |
| Ampere `m16n8k16` | **沒有**。`mma.cuh` 在 `__CUDA_ARCH__ < 800` 拆成 2× 或 4× `m16n8k8` | 不要直接寫 k16 |
| `ldmatrix.sync.aligned.m8n8.x2/.x4[.trans].b16` | smem → MMA fragment | **餵 TC 的正確搬法**。指標 16-byte 對齊 |
| `movmatrix.sync` | 暫存器裡轉置 8×8 | `mma.cuh` 有包；CUDA 11.8+ |
| `wgmma` / TMA / `cp.async` | **沒有** | 寫了是死碼或編不過 |

`mma.cuh` 的約定（跟 WMMA 不一樣，不要混）：

- A：row-major，M×K
- B：column-major，K×N
- C：column-major，M×N
- `load_ldmatrix` 的指標必須是 **smem、16-byte 對齊**；未對齊是 UB

TC 要 **整條 warp 32 lane 一起發**。divergence 的 warp 不要發 HMMA。

### Tile 要多大才餵得飽

CUTLASS sm_75 常見：128×128 或 128×256，K tile 32，double buffer。  
我們 GDN wmma 的 128×**16**（N=16）太瘦：算術強度低、setup／sync 吃掉 HMMA。

粗算一顆 SM 的 TC：每拍 1024 FLOP。要讓 8 顆 TC 有事做，K 迴圈跟 N 維都不能是「16 然後結束」。

skinny GEMV（序列 GDN 的 `Sᵀk`）本質是 GEMV，**不該先上 TC**。要把 token 合成夠大的 GEMM（而且 regs 還能住 ≥8 warp／SMSP）才划算。lab 已證：CS=16 的 wmma chunk 比 occ4 慢 4.5×。

## 記憶體層

| 層 | 數字 | 延遲／頻寬量級 | 刻 kernel |
|---|---|---|---|
| 暫存器 | 256 KB／SM = 4×64 KB | 0 cycle（scoreboard 另計） | 序列 state 放這裡（occ4） |
| smem | carveout 32 或 64 KB；**32 banks × 4 B／拍** | ~20 cycle | `bank = (byte_addr / 4) % 32`。同 bank 不同址 → 序列化 |
| L1 | 沒佔 smem 時可到 64 KB；與 texture 統一；**write-through** | 比 Pascal 低延遲、高頻寬 | occ* 應 carveout **偏 L1**（32 smem／64 L1） |
| L2 | **5632 KB**，11 個 512 KB 分區跟記憶體控制器綁 | | 一層 GDN state 48×128×128×4 ≈ **3.0 MB**，下一層就擠掉 |
| GDDR6 | 352-bit × 14 Gbps = **616 GB/s** | | 16 GB 權重／步 ⇒ decode 紙上 **~38 t/s** |

靜態 `__shared__` 預設上限 **48 KB**。要用滿 64 KB：動態 smem + `cudaFuncSetAttribute(..., MaxDynamicSharedMemorySize, n)`。本機 `sharedMemPerBlock` 預設回報 49152，就是這條。

### Bank conflict 與 swizzle

```
bank_id = (byte_address / 4) % 32
```

warp 32 lane 同時打 32 個不同 bank → 一拍完成。  
n-way conflict → 吞吐變 1/n。

常見解：

- padding：`[rows][cols+1]`，浪費 smem（這張卡只有 64 KB，別濫用）
- **XOR swizzle**（CUTLASS 預設）：`col_swz = col ^ (row * scale)`，零額外容量

`st.shared.v4`／128-bit store 更容易踩 conflict，要對 swizzle 一起設計。

### 這顆沒有的記憶體功能（不要抄 Ampere 部落格）

| 功能 | 從哪一代 | 這張卡 |
|---|---|---|
| `cp.async` / `LDGSTS` | sm_80 | **0**（我們 SASS 已確認） |
| TMA | Hopper | 無 |
| L2 persisting / `cudaAccessPolicyWindow` | sm_80 | API 叫了也沒那塊硬體 |
| 獨立 shared 與 L1（Pascal 以前那種） | 舊 | Turing 是 **96 KB 統一** |

Prefetch 只能：`LDG` 進暫存器（或 L1），跟 INT 管線的位址計算重疊。沒有非同步拷到 smem 的硬體。

L1 可 cache store（write-through）。Tuning Guide 說：Turing 上「顯式 smem」跟「直接打 global、靠 L1」的差距比 Pascal 小；spill 也比較不痛。但仍不要用 spill 當設計。

### 記憶體控制器與 partition camping

11 個控制器。極端的 stride（剛好是 11 個 sector 的倍數）可能打在同一分區。一般連續 `float`/`float4` load 沒這問題。GDN 的 `S[col*128 + i]` 讓同 warp 的 i 連續，是對的。

Sector 典型 32 B。一次 `float4` = 16 B，兩次才填一個 sector；向量化 load 仍然值得。

## Occupancy 速算（這張卡）

本機上限：32 warp、1024 thread、16 block、65536 regs、65536 B smem／SM。

```
blocks_by_warp  = 32 / warps_per_block
blocks_by_reg   = 65536 / (threads_per_block * regs)     # 粗算；精算用上面 SMSP 式
blocks_by_smem  = 65536 / smem_per_block                 # 0 smem → 不受限
blocks_by_max   = 16
active_blocks   = min(那四個)
occupancy       = active_blocks * warps_per_block / 32
```

精算一定要再跑 SMSP 那條：`32 * regs * ceil(warps_per_block/4) ≤ 16384`。

## 已量過的 GDN 怎麼坐在 layout 上

T=512、27B 形狀（Sv=128 Hq=16 Hv=48）。細節與 27B 端到端：`kernels.md`、`results.md`。

| kernel | regs | smem | 每 SMSP warp | occ. | T=512 |
|---|---:|---:|---:|---:|---:|
| serial | 255+spill | 0 | 1 | 12.5% | 1.83 ms |
| occ（ggml 同構） | 38 | 0 | 8 | 100%、~1-way ILP | 1.53 |
| occ2 | 47 | 0 | 8 | 100% + 2-way | 1.29 |
| occ4 | 62 | 0 | 8 | 100% + 4-way | 1.02 |
| occ4p | 64 | 0 | 8 | 100% + 4-way + prefetch | 0.92 |
| **occ8** | **96** | 0 | **5** | **62% + 8-way** | **0.91** |
| twopass chunk | 128 | 小 | — | ILP 被 C×C／launch 吃掉 | 6.89 |
| wmma chunk | 254 + 59 KB | 動態 | **2** | 25%；48 block 閒 20 SM | 5.00 |

occ8 贏 occ4：8-way ILP 補得過 occupancy 從 100% 掉到 62%。occ4p 跟 occ8 打平。  
wmma 輸：254 regs 把每個 SMSP 鎖成 2 warp；N=16；`HADD2` 還可能跟 HMMA 搶管線。SASS 有 HMMA×96 **不能**當比較快的證據。

## 照這顆卡該用的技巧（清單）

1. **先算 SMSP 暫存器**，再決定 COLS／tile／要不要 WMMA。
2. 序列 recurrence：先 **多欄 ILP** + **INT／FP 雙發 prefetch**。不要先上 TC。
3. 真的要用 TC：`ldmatrix` + `mma.sync.m16n8k8`（抄 `mma.cuh`，不要自己排 fragment）；tile ≥ 128×128 量級；regs 留到 ≥8 warp／SMSP（大約 ≤64 regs／thread @ 8 warp）。
4. smem：XOR swizzle，32 banks；64 KB 上限別用 padding 浪擲。
5. occ*：`cudaFuncAttributePreferredSharedMemoryCarveout` 偏向 **L1**。smem 大戶才偏 64 KB smem。
6. 向量化 `float4`／`LDG.128`，連續 lane 打連續址。
7. 4-warp block 對 4 scheduler；不要無故上 1-warp block。
8. warp reduce 用 `*_sync`。
9. **禁止當「最佳化」抄進來的：** `cp.async`、TMA、`wgmma`、BF16 MMA、`m16n8k16`、L2 persisting、Ampere ping-pong producer/consumer（那套吃 232 regs，這顆 SMSP 裝不下）。
10. Decode 再快也過不了 616 GB/s／權重。MTP 見 `results.md`。
